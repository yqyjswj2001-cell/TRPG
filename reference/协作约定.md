# 协作约定

## 第一次参与

先读仓库首页和 `AGENTS.md`，再看[采用清单](采用清单.md)。本仓库集中维护《东荒》的世界观、玩法规则和内容资料。

## 修改流程

1. 先开 Issue，或在已有 Issue 下说明准备修改的内容与文件，避免两人同时改同一段。
2. 从最新 `main` 建自己的分支，例如 `setting/地区补充`、`fix/条目纠错`。一次修改只处理一个主题。
3. 修改后提交 PR，写清改了什么、为什么、影响哪些既有设定。另一位维护者阅读后确认，再合并。
4. 合并前处理讨论中的问题；修改范围有明显变化时重新确认。日常不直接推送 `main`，不强推、不删除主分支。

GitHub 的强制审核需要在仓库设置中实际启用；写在文档里不等于已启用保护。建议 `main` 要求 1 位审核者批准、处理完讨论、更新内容后旧批准失效，并禁止强推与删除；当前没有程序测试，不设置不存在的必过检查。

## 哪份内容说了算

| 内容 | 位置与维护方式 |
| --- | --- |
| 某个团实际采用的规则 | 在[采用清单](采用清单.md)登记明确的文件、章节和确认记录 |
| 世界观与玩法规则 | `world/`；修改前说明是纠错还是提出修订版本 |
| 静态数值与规则表 | `rules/`；`source`、`source_commit` 用于溯源，修改时核对参数含义与适用范围 |
| 地点、人物、功法、物品等资料 | `data/`；保留已有编号、字段及一行一条的 JSONL 格式 |
| 创作词表、引用与取舍说明 | `reference/` |

同一主题在正文、数值表、完整资料、分片或 sample 中重复出现时，PR 要列出相关文件和需要同步的部分。尚未核实对应关系时，不用 sample 批量覆盖完整资料，不自动合并同名条目，不凭空补数值。无法确定的冲突先记为待讨论，不能让 AI 自行决定哪份最高。

新增条目先查是否重名或重复；已有 ID 不随意更换，删除前检查引用。只修改必要条目，避免全库排序、格式化或重新生成造成无关差异。改名和迁移须同步链接。

## 内容与验证

- 新设定标为提案；只有经协作确认并登记，才改为已采用。保留来源、理由和关联 PR。
- 数值变更同时解释作用、单位与适用范围，不把假设试算写成平衡已验证。
- Markdown 检查链接和前后矛盾；JSON / JSONL 检查语法、字段、已有 ID 和相关引用。只做与修改有关的一到两轮检查。
- 不提交运行存档、账号、真实群聊、密码或 Token。`.gitignore` 只防止匹配的未跟踪文件入库，不能清理已有历史或识别正文中的秘密。

## 署名与分工

各用各的 GitHub 账号，按 Issue 认领任务，按 PR 保留贡献记录；不共享账号或密钥。引用与授权按[资料来源与署名](资料来源与署名.md)记录。
